Caching is the art of answering a question you have already answered without doing the work twice. The first time a request arrives, the system computes the response the slow way: it queries the database, renders the template, and stores the result under a key derived from the request. The next identical request skips the computation entirely and returns the stored copy. The savings are real, but so are the hazards. A cache that never expires serves stale answers forever, and a cache that expires too aggressively provides no benefit at all while still paying the memory cost.

Invalidation is where caching earns its reputation as one of the hard problems. When the underlying data changes, every cached response derived from that data becomes a lie. The simplest policy is time based expiration: every entry carries a lifetime, and after the lifetime passes the entry is recomputed on the next request. Time based expiration is easy to reason about but imprecise, because the lifetime is a guess about how quickly the data changes. Event based invalidation is precise but demands that every write path knows which cache keys it poisons, and that knowledge decays as the codebase grows. Most production systems blend the two: short lifetimes as a safety net, explicit invalidation for the paths that matter.

A relational database organizes data into tables of rows and columns, and its query planner decides how to satisfy each query. When a query filters on a column without an index, the planner has no choice but to scan the entire table, reading every row and testing the predicate against each one. An index changes the arithmetic completely. A balanced tree over the column values lets the database seek directly to the matching rows, turning a scan proportional to the table size into a lookup proportional to its logarithm. The index is not free: every insert and update must maintain it, and the write amplification compounds with every additional index on the table.

Transactions exist because partial failure is worse than failure. A transfer between two accounts must debit one and credit the other; performing only half of that work corrupts the books. The database wraps both writes in a transaction, and the transaction commits atomically or not at all. Isolation levels control how much concurrent transactions can observe of each other. Serializable isolation behaves as if transactions ran one at a time, which is the easiest model to reason about and the most expensive to provide. Weaker levels admit anomalies with names like dirty read and phantom read, and choosing a level means deciding which anomalies your application can survive.

Distributed systems begin with an admission: the network is not reliable. Messages are delayed, duplicated, reordered, and dropped, and no machine can distinguish a slow peer from a dead one. Every design in the field is a response to that admission. Replication keeps copies of data on several machines so that losing one machine does not lose the data. Consensus protocols let a cluster agree on a single sequence of decisions even while some members are failing, at the cost of round trips that place a floor under latency. The famous impossibility results are not curiosities; they are fences around the design space, and systems that pretend the fences are not there tend to demonstrate why they are.

A queue decouples the producer of work from the consumer of work. The web request that triggers an email does not send the email; it enqueues a message describing the email and returns immediately. A worker process dequeues the message and performs the slow, failure prone delivery on its own schedule. The queue absorbs bursts, smooths load, and isolates failures, but it introduces its own questions. Delivery guarantees come in flavors: at most once delivery may drop work, at least once delivery may repeat it. Exactly once delivery is a slogan rather than a property, and the honest version is at least once delivery paired with idempotent handlers, so that repeating a message changes nothing.

Idempotency deserves its own paragraph, because it is the property that makes retries safe. An operation is idempotent when performing it twice has the same effect as performing it once. Setting a value is idempotent; incrementing a value is not. Real systems achieve idempotency with deduplication keys: the caller attaches a unique identifier to the request, the server records identifiers it has already processed, and a duplicate arrival is acknowledged without being reapplied. The technique is simple and the discipline is not, because every handler that touches money or inventory has to honor it without exception.

Testing is the practice of making claims about code precise enough to be checked by a machine. A unit test isolates one function and asserts on its behavior across normal inputs, boundary inputs, and malformed inputs. An integration test exercises a path through several components and catches the failures that live in the seams between units, which is where a disproportionate share of production incidents originate. The pyramid metaphor suggests many unit tests, fewer integration tests, and fewer still end to end tests, on the grounds that the broader a test reaches, the slower it runs and the harder its failures are to localize.

A flaky test is a test that passes and fails without any change to the code under test, and it is more corrosive than a missing test. The first time the suite fails spuriously, an engineer investigates. The tenth time, the engineer retries the build without looking. From that point the suite has trained its audience to ignore it, and a genuine regression rides in unexamined behind the noise. The cures are unglamorous: remove hidden dependence on time and ordering, seed every source of randomness, and quarantine nothing, because a quarantined test is a deleted test that still costs maintenance.

Version control gives a team a shared, append only history of the code. Each commit records a snapshot, its parent, an author, and a message explaining why the change exists. Branches let work proceed in parallel without collision, and merging reconciles divergent histories, mechanically when the changes do not overlap and manually when they do. The discipline that makes history valuable is small, coherent commits with messages that explain intent rather than restating the diff. A history of tiny, well described changes is an instrument for debugging; a history of enormous commits labeled with a single vague word is ballast.

Code review is the habit of having a second person read a change before it merges. The reviewer catches bugs, but the durable value is subtler: review spreads knowledge of the codebase across the team, holds interfaces to a consistent standard, and surfaces design disagreements while they are still cheap to resolve. Review works when changes are small enough to hold in one head and authors describe intent honestly. It fails when a thousand line change arrives with the description fix bugs, and the reviewer, facing an unreadable wall, approves it on faith.

Deployment is the act of replacing running software with a newer version without breaking the users currently depending on it. A rolling deployment replaces instances a few at a time, watching health checks between batches, so that a bad release is caught while most of the fleet still runs the old version. Blue green deployment keeps two complete environments and flips traffic between them, buying instant rollback at the price of doubled infrastructure. Canary releases route a small fraction of traffic to the new version and compare its error rate against the old before committing. All three are expressions of the same instinct: never bet the whole system on untested code in one motion.

Rollback is the plan you make while everything still works. When a release goes wrong, the fastest path to health is almost always reverting to the previous version rather than diagnosing under pressure and shipping a fix forward. That option exists only if releases are reversible, which is a property that must be designed and rehearsed. Database migrations are the classic complication, because a schema change that the old code cannot read converts rollback from a routine action into an incident of its own. The discipline is to make migrations backward compatible for at least one release, so the arrow of deployment can always be reversed.

Latency is the time between asking and receiving, and averages hide almost everything interesting about it. A service can hold a flattering mean latency while its slowest percentile is catastrophic, and the slow tail is what users remember, because a page that issues a hundred requests experiences the tail of the distribution on nearly every load. Percentiles resist that distortion, which is why service objectives are stated against them. Throughput measures work per unit time, and the two trade against each other: batching raises throughput while adding wait, and systems pushed near saturation see queueing delay dominate everything else.

Memory management determines how a program obtains and returns the memory it works with. Manual management gives precise control and precise opportunities for use after free and leaks. Garbage collection removes that class of bugs by periodically finding unreachable objects and reclaiming them, paying instead with pause times and memory overhead. Reference counting reclaims objects the moment the last reference disappears, but cycles of objects that reference each other never reach a count of zero, so practical collectors pair counting with a cycle detector. Ownership systems move the discipline to compile time, proving at build time that every allocation has exactly one responsible owner.

The compiler translates source code into a form a machine executes, and its middle stages are where the interesting work happens. Parsing turns text into a tree, analysis attaches types and scopes to the tree, and optimization rewrites the program into a faster equivalent: folding constants, eliminating dead branches, hoisting loop invariant work, and inlining small functions to expose further rewrites. An interpreter executes the tree or a compact bytecode directly, trading startup speed for peak speed. Just in time compilation watches the running program, discovers which paths are hot, and compiles exactly those, an empirical bet that the recent past predicts the near future.

Concurrency is structuring a program as independently progressing activities; parallelism is running them at the same instant on separate hardware. A program can be concurrent on one core, interleaving its activities, and the distinction matters because the bugs differ. Shared mutable state guarded by locks invites deadlock when two activities each hold what the other needs. Message passing avoids shared state by giving each activity private data and a mailbox, at the cost of copying and coordination overhead. Data races, where two activities touch the same memory without synchronization and at least one writes, produce corruption that no single threaded test will ever reproduce.

Encoding is the bridge between the abstraction of text and the reality of bytes. A character set assigns numbers to characters; an encoding decides how those numbers are laid out in memory. The dominant encoding on the wire represents common characters in a single byte and rarer characters in two, three, or four, which keeps documents in some scripts compact while making the byte length of a string and its character length two different questions. Systems that confuse those questions truncate text mid character and emit garbage. The rule that survives contact with production is to decode bytes into text at the boundary, work in text everywhere inside, and encode back to bytes only on the way out.

Logging is the narrative a system writes about itself. Structured logs, where each event is a set of named fields rather than a prose sentence, can be filtered and aggregated by machines, which is the only way narratives survive at scale. Log levels encode urgency, and their misuse is a genre of its own: warnings that fire on every request train operators to filter warnings, which conceals the one warning that mattered. The volume question is economic, because storage and indexing are priced per byte, and a chatty debug line inside a hot loop can cost more than the feature it debugs.

Rate limiting protects a service from demand it cannot survive, whether the demand is an attack, a misconfigured client, or simple popularity. The token bucket algorithm gives each client an allowance that refills at a steady rate and drains with each request, permitting short bursts while capping the sustained rate. When the allowance is empty the service refuses politely, and a well behaved client backs off exponentially with jitter, spreading its retries so that a thousand rejected clients do not return in the same synchronized instant they were refused. Retrying without backoff turns a brief overload into a self sustaining storm.

Serialization converts an in memory structure into bytes that can cross a network or rest in a file, and deserialization performs the return journey. Text formats are readable by humans and debuggable with ordinary tools, while binary formats are smaller and faster to parse. The questions that decide between them are about evolution: what happens when a field is added, renamed, or removed while old readers and writers are still running. Formats with explicit schemas can promise compatibility across versions; formats without schemas make every reader responsible for tolerating surprises, and readers are rarely that tolerant in practice.
